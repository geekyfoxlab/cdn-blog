# 开发流程与项目交接

> 本文按 SSD（需求规格、设计、实现、验证、交付）思路整理，作为 Example Lab 博客的长期维护和二次开发入口。

## 1. 项目识别

| 项目项 | 当前值 |
| --- | --- |
| 项目名称 | Example Lab Blog |
| 代码仓库 | `example/example-blog`（GitHub 私有仓库） |
| 默认分支 | `main` |
| 生产域名 | `https://blog.example.com` |
| Pages 项目 | `example-blog` |
| Pages 备用地址 | `https://example-blog.pages.dev` |

## 2. SSD 工作流

任何功能、内容或基础设施变更都按以下顺序推进。小改动可以合并步骤，但不能省略验收和记录。

```text
需求/问题
  -> 需求规格（范围、验收标准、风险）
  -> 方案设计（影响文件、配置、回滚点）
  -> 分支实现
  -> 本地验证
  -> 预览部署与浏览器验收
  -> 合并 main / Pages 发布
  -> 生产复核与交接记录
```

### 2.1 需求规格

在 Issue、任务说明或变更记录中写清：

- 背景和目标：要解决什么问题，面向读者还是维护者。
- 范围：涉及页面、文章、配置、DNS 或第三方服务的具体边界。
- 非目标：明确不修改主站、根域、`www`、MX/TXT 或无关子域。
- 验收标准：页面/路由、HTTP 状态、SEO、移动端、隐私和构建结果如何判断完成。
- 风险与回滚：失败时恢复哪一个提交、Pages 部署或 DNS 记录。

需求不清楚时，先补充规格，不直接扩大实现范围。真实姓名、邮箱、社交账号和个人经历必须由站长提供，不能从占位文案推断。

### 2.2 方案设计

设计记录至少包含：

1. 受影响的文件和模块。
2. 选择现有模式的理由，以及不采用方案的原因。
3. 数据/配置是否进入静态页面，是否会增加第三方请求。
4. 本地、预览、生产三个环境的差异。
5. 最小回滚动作和需要保留的证据。

业务域名、SEO、导航、联系方式、主题色、图标/图片路径和功能开关只从 `src/config/site.ts` 读取；不要在组件中复制这些值。文章内容放在 `src/content/posts/`，静态公开文件才放在 `public/`。

### 2.3 分支与实现

```sh
git switch main
git pull --ff-only
git switch -c feat/<short-name>
```

主题/依赖升级使用 `codex/upgrade-YYYYMMDD` 或等价的独立分支。一次分支只处理一个可描述的变更集；不要把未相关的格式化、重命名或账号配置混入提交。

推荐提交格式：

```text
feat: add article metadata
fix: prevent stale search results
docs: record custom domain handoff
chore: upgrade Astro dependencies
```

不要提交 `dist/`、`.env*`（示例文件除外）、浏览器截图中的凭据、API Token、密码、私钥、数据库连接串或私有内容。

### 2.4 本地验证

在 Node.js 22 和 pnpm `9.14.4` 下按顺序执行：

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm type-check
pnpm exec biome check ./src
pnpm build
```

随后使用构建产物进行浏览器验收：

```sh
pnpm preview --host 127.0.0.1 --port 4322
```

至少检查首页、About、归档、公开文章（如有）、404、搜索、RSS、Sitemap、robots、深浅色切换、移动端布局和主站链接。确认 Giscus 与 Cloudflare Web Analytics 在关闭时没有第三方脚本请求。

### 2.5 预览、合并与发布

Pull Request 需要说明变更、验收结果、风险和回滚点。合并前确认：

- CI 或本地四项检查全部通过。
- 生产构建没有草稿路由、草稿媒体或临时文章。
- 页面截图/链接能复现验收结论。
- 文档、配置和实际行为一致。

合并 `main` 后由 Cloudflare Pages Git 集成自动构建。固定参数为：`pnpm build`、`dist`、Node.js 22、pnpm `9.14.4`。发布后记录 Pages 部署 ID、时间、提交 SHA 和线上检查结果。

## 3. 变更类型与完成定义

| 类型 | 主要入口 | 最低验收 |
| --- | --- | --- |
| 文章 | `src/content/posts/` | Frontmatter、正文链接/图片、草稿边界、构建和搜索 |
| 站点文案/导航/外观 | `src/config/site.ts` | 页面文案、联系方式、主题色、图标/背景图、内外链、Canonical/OG、构建 |
| 组件/样式 | `src/components/`、`src/styles/` | 类型检查、桌面/移动端、键盘和主题切换 |
| Markdown 管线 | `src/plugins/`、`src/content.config.ts` | Markdown、Mermaid、图片、代码块和 SEO 回归 |
| 依赖/主题 | `package.json`、锁文件、上游记录 | 独立分支、全量检查、Pages 预览和回滚 |
| 部署/DNS | Cloudflare 控制台、文档 | `pages.dev`、自定义域 HTTPS、HTTP 状态、仅改授权记录 |

完成定义（DoD）：源码已审查，文档已同步，本地验证通过，预览或生产验收可复现，提交可回滚，且没有凭据泄漏或越权改动。

## 4. 当前部署与 DNS 交接

### 4.1 代码与托管

- GitHub 私有仓库：`example/example-blog`。
- Cloudflare Pages：`example-blog`，Git 集成只授权该仓库。
- `main` 推送触发构建；不要在仓库保存 Cloudflare API Token。
- `pages.dev` 是故障排查和回滚时的备用入口，生产 Canonical 仍使用博客域名。

### 4.2 域名边界

当前只使用并维护 `blog.example.com`。Cloudflare Pages 自定义域已显示活动，SSL 已启用，DNS 控制台记录为代理 CNAME：

```text
blog.example.com CNAME example-blog.pages.dev（Proxied）
```

根域 `example.com`、`www`、MX/TXT、邮件记录和其他子域不属于本项目，禁止在博客发布流程中修改。解析检查应使用至少两个独立网络；代理 CNAME 对外可能显示 Cloudflare A 地址，不能据此手工改成 IP。

### 4.3 线上验收记录（2026-07-31）

- `https://blog.example.com/`、`/about/`、`/archive/`、`/rss.xml`、`/sitemap-index.xml`、`/robots.txt` 返回 200。
- 不存在路径返回 404；证书校验通过并覆盖 `blog.example.com`。
- SSD 交接基线部署 `00000000-0000-4000-8000-000000000000` 已完成，构建提交为 `example-baseline-sha`。
- 系统 Chrome 已检查页面导航和 Pagefind，搜索 `Python` 可命中 About 内容。
- 当前没有公开文章，首页显示“暂无公开文章”是预期状态。
- DNS 某些本地/递归解析结果可能暂时保留旧 A 记录；以 Cloudflare 控制台、独立 DoH 查询和 HTTPS 实际响应共同判断，继续观察传播，不修改根域。

## 5. 二次开发接手清单

### 5.1 接手前

1. 获取 GitHub 仓库、Cloudflare Pages、域名 DNS 的最小必要权限；权限通过密码管理器或组织成员管理，不写入仓库。
2. 阅读本文、[架构与目录结构](02-架构与目录结构.md)、[本地开发](03-本地开发.md)、[站点配置](05-站点配置.md) 和 [主题升级指南](12-主题升级指南.md)。
3. 安装 Node.js 22、pnpm `9.14.4`，运行完整本地检查。
4. 打开 `src/config/site.ts`，确认博客与主站地址、联系方式、主题色、图标/背景图、功能开关和占位资料。
5. 在 Cloudflare Pages 查看最近成功部署、构建日志、环境变量名称和自定义域状态，不复制或打印变量值。

### 5.2 开发前核对

- `git status --short` 无意外修改，`git log` 能定位最近生产提交。
- 文章和图片没有放入 `public/` 的敏感位置。
- 本地评论已按隐私决策启用；若要改为公开评论或启用统计，先更新配置文档和隐私说明。
- 域名任务明确只针对 `blog`，涉及根域或 Nameserver 时停止并重新确认范围。

### 5.3 交付给下一位维护者

交付包应包含：变更规格、设计取舍、提交 SHA、检查命令与结果、预览/生产 URL、Pages 部署 ID、DNS 旧值/新值、已知风险、回滚步骤和待办事项。凭据只交给账号管理员，不放在交付文档、截图、Issue 或聊天记录中。

## 6. 回滚与事故处理

1. **代码问题**：先回到 `pages.dev` 验证，使用审查后的 revert 提交或 Pages 上一份成功部署回滚。
2. **构建问题**：固定 Node/pnpm，查看首个构建错误；不要直接编辑 `dist/` 或删除部署历史。
3. **域名问题**：保留 `pages.dev`，检查自定义域证书和 `blog` 记录；不得通过修改根域解决。
4. **DNS 回滚**：只恢复最后一次验收通过的 `blog` 记录，等待 TTL/缓存传播；本次迁移前旧 A 没有承载项目，不作为默认回滚目标。
5. **安全事件**：立即撤销/轮换泄露凭据，保留日志，检查 Git 历史和 Pages 构建产物，再决定是否暂停部署。

## 7. 决策记录入口

重要决策至少同步到本文或对应专题文档，包含日期、背景、选择、替代方案、影响和回滚点。当前已记录的决策包括：

- 使用 GitHub 私有仓库 + Cloudflare Pages Git 集成和 CDN。
- 只绑定博客子域，不迁移根域和 Nameserver。
- 本地评论启用且不引入后端；Giscus 第三方评论和 Cloudflare Web Analytics 默认关闭；PWA、后端和数据库暂不引入。
- 生产构建过滤草稿，Pagefind 只索引公开页面。

后续若新增后端、账号、评论、统计、自动发布或主站联动，应新建独立规格和验收记录，不把隐含依赖直接加入博客构建。
