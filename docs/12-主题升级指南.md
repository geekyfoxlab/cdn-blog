# 主题升级指南

## 当前基线

博客基于 Fuwari 上游提交 `6d39b0dec41282e7852e23e032998a5789abee28`，当前 Astro 为 `5.13.10`，Svelte 为 `5.45.5`，目标 Node.js 为 22、pnpm 为 `9.14.4`。上游没有稳定 Git tag，因此升级必须以提交 SHA、依赖锁文件和本地验证结果共同记录。

当前仓库已推送到 GitHub 私有仓库 `example/example-blog` 的 `main` 分支，并由 Cloudflare Pages 自动发布。升级流程仍不自动创建远程资源，也不改变 DNS。

## 升级原则

- 优先合并 Fuwari 上游的主题修复和可访问性改进，避免复制整棵上游目录。
- `src/config/site.ts` 是博客业务配置源，不得被上游 `src/config.ts` 覆盖。
- 自定义 Astro 集成、Remark/Rehype 插件、SEO、草稿边界、图片和 Mermaid 逻辑应保持可识别的独立差异。
- 每次升级只处理一个主题/依赖变更集，保留可回滚的分支和构建产物记录。
- 不为暂未需要的 PWA、后端、AI 服务或自部署统计提前引入运行时依赖。

## 升级前

1. 阅读 [上游基线](00-upstream-baseline.md)，记录当前上游 SHA、版本和已知警告。
2. 检查 `git status --short`；未提交的文章和配置先单独保存，不覆盖用户工作。
3. 创建升级分支，例如 `codex/upgrade-fuwari-YYYYMMDD`（分支创建本身也需按项目协作约定执行）。
4. 保存当前通过的检查结果和 `dist/` 关键页面快照；不要把 `dist/` 加入版本控制。
5. 阅读上游变更、Astro/Svelte 兼容矩阵和依赖 release notes，标出可能影响 Markdown、Swup、图片和主题切换的项目。

## 合并顺序

建议按以下边界逐组处理：

1. 先更新直接依赖与锁文件，保持 `packageManager: pnpm@9.14.4`，必要时在 Node 22 环境安装。
2. 再合并主题类型、布局和组件，逐个解决本地差异，不使用整文件覆盖。
3. 复核 `src/config/site.ts` 到 Fuwari 兼容层的字段映射、`blogConfig.appearance`、导航外链和作者占位。
4. 复核 Markdown 管线的插件顺序：草稿图片 guard、数学、Mermaid、图片 Caption、标题锚点和 Expressive Code。
5. 复核 `siteUrl` 仍是 `https://blog.example.com`，主站链接仍是 `https://example.com`。
6. 只有在上述内容稳定后，才更新文档和版本记录。

## 必须保留的本地差异

以下范围不是可随意删除的“主题杂项”：

- 业务配置和主站/博客解耦：`src/config/site.ts`、兼容层和导航组件。
- SEO、Canonical、RSS、Sitemap、robots、404 和公开草稿过滤。
- Mermaid 严格安全模式、主题切换/Swup 重绘与源码回退。
- 响应式正文图片、Caption、PhotoSwipe 和公开文章封面清单。
- Giscus 与 Web Analytics 的默认关闭、环境驱动和生产边界。
- CI 的 Node 22、锁文件安装、Astro 检查、类型检查和 Pagefind 构建。

合并冲突时，先理解两侧行为再修改；不要用 `git checkout --` 或 `git reset --hard` 丢弃未提交内容。

## 验证顺序

不要并行启动多个 Astro/Vite 进程，避免虚拟模块和缓存互相干扰。使用目标 Node/pnpm 版本按顺序执行：

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm type-check
pnpm exec biome check ./src
pnpm build
```

随后使用 `pnpm preview` 做浏览器验收：

- 首页、About、归档、公开文章、标签/分类和 404。
- RSS、Sitemap、robots、Canonical、Open Graph、JSON-LD。
- 草稿不生成路由、RSS、Sitemap、Pagefind 条目或仅被草稿引用的 Astro 媒体。
- Mermaid 在首次加载、深浅色切换和 Swup 页面切换后都只保留一个 SVG，并提供可读标题/描述与源码回退。
- 图片 `srcset`、尺寸、Caption、PhotoSwipe、移动端布局和键盘操作。
- Giscus/Analytics 默认关闭时不加载第三方脚本；启用测试必须使用专门的非生产变量。

若升级改变了生成的 URL、缓存策略或第三方脚本请求，必须在部署文档中记录决策和回滚点。

## 回滚与发布

- 本地验证失败：保留升级分支，修复或放弃该分支；不要覆盖主分支未提交工作。
- 已提交但未发布：通过审查后的 revert 提交回滚，保留失败日志供定位。
- 已由 Pages 发布：在 Pages 部署列表回滚到上一份成功部署，或让 Git 集成重新构建已知稳定提交。
- 自定义域异常：先回到 `pages.dev` 验证；不要通过修改根域 DNS 解决博客问题。

升级完成后，更新 [上游基线](00-upstream-baseline.md) 中的 SHA、版本、日期、差异和验证结果，再由维护者决定是否提交/推送。升级文档不授予远端操作权限。

## 需要特别复核的升级信号

- Astro 主版本、Svelte 编译器或 Swup 导航生命周期变化。
- `remark`/`rehype` AST 结构、Expressive Code HTML 结构或 Tailwind 处理顺序变化。
- 图片服务、Sharp、Mermaid 安全 API 或浏览器 CSP 变化。
- Pagefind CLI 参数、索引目录或 Cloudflare Pages 构建镜像变化。
- Node/pnpm 安装脚本白名单变化；只允许项目明确需要的构建脚本运行。
